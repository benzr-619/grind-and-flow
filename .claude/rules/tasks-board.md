# Tasks board — This Week / Next / Done drag-reorder

Session 2026-07-01. The board (`renderBoard()`'s non-project, non-calendar branch) renders `This Week`/`Next`/`Done` columns as `.col-body[data-col]` drop zones of `.card` elements (`backlog`/Inbox is reviewed separately — see [inbox-review](./inbox-review.md)).

**Later same session**: a `Recurring` column was added as a 4th, leftmost column (`data-cols="4"`) — it renders `.recur-card` elements via a separate `_renderRecurringCard`, isn't a generic drag/drop target, and isn't part of the reorder/board_order mechanics described below (no manual reordering — see [recurring-tasks rule](./recurring-tasks.md)).

## Bug found: reorder wasn't persisting
Dragging a card to a new position within a column showed a live placeholder (`_onDragOver` → `_dragAfterEl` → `.drag-placeholder`), but `_onDrop` never read that position — it only set `item.status = colId` and called `renderBoard()`. Since **This Week** and **Done** had no per-column manual-order field at all (This Week sorted purely by `scheduledDate`+`scheduledTime`; Done had no sort block — pure natural array order), any reorder was silently discarded on re-render. **Next** already had `dayOrder` (shared with the Week view's within-day stack) as its sort key, but `_onDrop` never wrote to it either, so Next reorders were equally lost.

## Fix
- New column: `tasks.board_order` (numeric, nullable; migration `add_board_order_to_tasks`), mapped as `boardOrder` in `data.js` (`_taskToDb`/`_taskFromDb`). Deliberately **not** reusing `dayOrder` for This Week/Done — `dayOrder` is semantically "priority within one calendar day" (Week view) and only meaningful for tasks with a `scheduledDate`; This Week mixes scheduled + unscheduled tasks across many days, so overloading `dayOrder` there would cross-contaminate Week view day-stacking with board-column ordering.
- `_onDrop(e, colId)` now computes a fractional order value (same midpoint-of-neighbors technique as `_onWeekDrop`) via `_dragAfterEl(container, e.clientY)` and writes it to `dayOrder` when `colId === 'next'`, else to `boardOrder`. Only applied when `item.type !== 'project'` (this drop zone is tasks-only in practice; the `item.type === 'project'` branch alongside it is legacy/defensive and never actually triggers).
- Column sorts updated: **This Week** = `boardOrder` asc (nulls last) → scheduled date+time → unscheduled last. **Done** = `boardOrder` asc (nulls last), ties keep natural order (stable sort). **Next** unchanged (`dayOrder` asc → `dueDate` → `dateAdded`) — only the write-path was missing there.
- The shared `_dragAfterEl(container, y)` helper (used by both the Tasks board and the Week view) also had a **separate** bug — see the Week view rule's Bug fix note in [calendar-week.md](./calendar-week.md) — its selector didn't match `.week-task` elements at all, so Week view day-column reorder was silently broken too. Fixed in the same pass by adding `.week-task:not(.dragging)` to its selector.

## Gotcha
`board_order` only exists on `tasks`, not `projects` or `archive` — don't read/write it off an item without checking `item.type !== 'project'` first (projects never sit in these `.col-body` columns today, but the drop handler's legacy project branch means the guard matters if that ever changes).

## Legibility pass + start-orb relocation (same session)
- **Font sizes scaled up** across cards/columns for legibility: `.card-title` 13→15px, `.col-name` 9→11px (weight 500→600), `.col-count` 9→10.5px, `.tag-pill` 9→10.5px, `.age-counter` 10→11px, `.card-project` 9.5→11px, `.card-sched-time`/`.card-day` 9.5→11px, `.focus-btn`/`.later-btn` 9.5→11px, `.blocked-badge` 9→10px, `.waiting-badge` 8→9.5px, `.card-waiting-reason` 12→13px, `.card-subtask-count` 9→10.5px. Type hierarchy (mono for meta/labels, display for titles) unchanged — only the scale.
- **Start-focus target relocated**: the old `.focus-drop-zone` was a horizontal bar `position:absolute; top:0` spanning the full `.columns` grid width, revealed only while `.columns.dragging-active` — it visually overlapped the top of all three columns during a drag and had **no click affordance at all** (drop-only). Replaced with `.next-start-orb`, a small persistent (always-visible, not drag-gated) circular button anchored at the bottom of the **Next** column's `.col-body`, after the `+ add` button.
  - **Drop target**: reuses `_onFocusDragOver`/`_onFocusDragLeave`/`_onFocusDrop` verbatim (unchanged — still resolves via module-scoped `dragId` → `startTask(dragId)`).
  - **Click target**: `onclick="App.startTask(firstDayOrderId)"` where `firstDayOrderId` is the same "top of Next" id already computed for the `.is-first` amber-ring card styling (first `dayOrder`-non-null item in the Next column). When Next has no `dayOrder`-tagged item, the orb renders `.disabled` (muted, no onclick) but **stays a valid drop target** (`cursor:copy`, not `pointer-events:none`) so drag-swap-to-start still works even on an "empty priority" Next column.
  - The `dragging-active` class toggle on `.columns` (`_onDragStart`/`_onDragEnd`/`_onFocusDrop`) was dead-coded away — nothing reads that class anymore.

## Live daily rollover (same session)
`_dailyRollover()` (advance overdue `this-week` tasks to today + auto-promote today's tasks into Next, capped) previously only ran once from `init()` on page load. `_scheduleMidnightArchive()` (the existing live-without-reload midnight timer, also used for stale-Done auto-archive) now also calls `_dailyRollover()` before its `renderBoard()`, so a tab left open overnight re-runs both the archive sweep and the rollover at the next midnight, then reschedules itself — same pattern, no new timer.
